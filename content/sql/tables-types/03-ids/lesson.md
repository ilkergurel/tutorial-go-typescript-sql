## Concept

Surrogate keys come in two families:

- **Counters**, drawn from a sequence. `bigint GENERATED ALWAYS AS IDENTITY` is the
  standard way since PostgreSQL 10; `serial`/`bigserial` is the older shorthand that
  expands to a column default calling `nextval()`. Both use a sequence object, and
  sequences hand out each value once, gaps included, without waiting for other
  transactions.
- **UUIDs**, 128-bit values anyone can generate without asking anyone. PostgreSQL 18 adds
  `uuidv7()`, a time-ordered UUID (millisecond timestamp first), next to `uuidv4()` (an
  alias of `gen_random_uuid()`). Ordered ids keep the primary-key index appending at one
  end, the way a sequence does, without the sequence.

## Coming from C/C++/Java/Python/JS

- **Java, Python, JS:** the built-in generators you know (`UUID.randomUUID()`,
  `uuid.uuid4()`, `crypto.randomUUID()`) make version 4: random, unordered. Fine for
  tokens, poor as a clustered sort order.
- **ORMs:** "auto-increment" maps to an identity column. If an ORM or an old tutorial
  generates `serial`, it works, but it's the legacy form.
- **Go:** `DEFAULT uuidv7()` plus `INSERT ... RETURNING id` lets the database mint the id,
  so the service needs no UUID library just for keys.
- **C:** think of a uuid as a 16-byte array compared like `memcmp`; v7 puts a big-endian
  timestamp in the first 6 bytes, which is why byte order equals time order.

## Design notes

A sensible default: `bigint GENERATED ALWAYS AS IDENTITY` for internal keys. Reach for
`uuid DEFAULT uuidv7()` when ids are created outside a single database (clients that work
offline, several services, merging data) or when sequential ids would leak volume ("order
4211" says you have had about 4,200 orders). Choose ALWAYS over BY DEFAULT unless loading
ids from elsewhere is routine; making the override explicit is the point.

v7 order is time order at millisecond granularity, which is what the docs promise.
PostgreSQL 18's generator additionally fills the next 12 bits with a sub-millisecond
fraction and keeps each new value above the previous one generated in the same session,
which is why the example's 1000 ids sort perfectly. The docs only list the parts
("millisecond precision + sub-millisecond timestamp + random"); the per-session step is
in the source (src/backend/utils/adt/uuid.c, function get_real_time_ns_ascending), and
on PostgreSQL 18.7 here 100,000 ids from one statement, about 960 per millisecond, came
out strictly increasing. Across sessions there is no such promise: ids are ordered by
the clock reading they embed, millisecond then fraction, and random bits only decide
between ids generated within about a microsecond of each other. That is roughly the order in which they were
generated, not the order in which their transactions commit.

The embedded timestamp is the price of that order. If creation time is sensitive, keep v7
as the internal key and expose a separate random token, or use v4 and accept the index
cost.
